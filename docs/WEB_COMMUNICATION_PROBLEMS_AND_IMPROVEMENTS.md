# 웹 대화·작업 관제 문제 분석과 개선안

## 문서 목적

이 문서는 Codex × Gemini Worker 웹을 실제로 사용하면서 반복적으로 발생한 소통 문제를 정리한다. 핵심 문제는 단순히 화면이 느린 것이 아니라, **대화·작업 실행·관제 상태가 하나의 흐름처럼 보이면서도 실제로는 서로 다른 프로세스와 상태 저장소를 사용한다는 사실이 사용자에게 드러나지 않는 것**이다.

이 문서의 목표는 다음과 같다.

- 사용자가 왜 작업이 멈췄다고 느꼈는지 설명한다.
- 실제 실행 상태와 화면 표시가 어긋난 대표 사례를 남긴다.
- UI 임시 처방이 아닌 백엔드 상태 모델까지 포함한 개선 방향을 제시한다.
- 협업자가 재현 테스트와 완료 기준을 바로 작성할 수 있게 한다.

## 사용자가 기대하는 경험

사용자가 기대한 흐름은 다음과 같다.

```text
사용자와 Codex가 대화한다
        ↓
Codex가 질문인지 작업인지 판단한다
        ↓
질문이면 즉시 대답한다
        ↓
작업이면 승인 후 오케스트레이터에 전달한다
        ↓
Codex·Gemini·검증기의 진행 상황이 작업 트리에 표시된다
        ↓
실패한 노드는 이유와 재시도 버튼을 제공한다
        ↓
완료되면 결과와 검증 증거를 알리고 활성 Worker 화면에서 사라진다
```

웹 채팅은 사용자와 Codex의 대화 공간이고, 프로젝트 관제실은 백그라운드 CLI 실행을 관찰하고 제어하는 공간이어야 한다. 두 화면은 같은 Run을 공유하지만 역할은 구분되어야 한다.

## 대표 문제 요약

| 우선순위 | 문제 | 사용자가 느낀 증상 | 핵심 원인 |
|---|---|---|---|
| P0 | 질문도 작업으로 실행됨 | “잘 들려?”에도 계획 수립과 Worker가 표시됨 | 요청 분류 없이 모든 입력을 Run으로 변환 |
| P0 | 화면 상태와 실제 프로세스 불일치 | 실행 중인데 실제 Run 폴더나 Worker가 없음 | Dashboard Run과 Router Run의 결합 부족 |
| P0 | 허위 진행 단계 표시 | 실행 증거가 없는데 계획·도구 실행 완료 표시 | 시간 기반 또는 낙관적 타임라인 생성 |
| P0 | 종료·실패 원인이 사라짐 | “프로세스 종료/상태 기록 불일치”만 표시 | stdout, stderr, exit code 미보존 |
| P1 | 응답이 완성될 때까지 보이지 않음 | CLI 결과를 마지막에 복사한 것처럼 보임 | 토큰·이벤트 스트리밍 미지원 |
| P1 | 작업 완료를 알 수 없음 | 사용자가 계속 “끝났냐?”고 물어봐야 함 | 완료 알림과 terminal event 부재 |
| P1 | 종료 Worker가 계속 활성으로 남음 | 관제실의 실행 수와 실제 상태가 다름 | heartbeat 만료와 종료 정리 규칙 부족 |
| P1 | 새로고침으로 복구되지 않음 | 오래된 실패 화면이 그대로 남음 | 메모리 상태와 디스크 상태 재조정 부족 |
| P1 | 내부 협업 과정이 불투명함 | Codex와 Gemini가 무엇을 주고받는지 모름 | 상위 이벤트 요약과 작업 트리 부재 |
| P1 | 재시도 경로가 없음 | 실패할 때 다시 채팅으로 설명해야 함 | 실패 노드 단위 재시도 계약 부재 |
| P2 | 승인 의미가 불명확함 | 왜 승인해야 하는지 알기 어려움 | 승인 대상 diff·명령·위험 정보 부족 |
| P2 | 사용량 표시가 혼란스러움 | 남은 양, 초기화 시각, 조회 가능 여부가 모호함 | 공급자별 사용량 계약과 갱신 시각 부재 |
| P2 | Windows 실행 환경에 취약함 | 한글 경로, PowerShell, CLI 경로 오류 | 실행기 탐색·UTF-8·인자 전달 표준화 부족 |

## 문제별 상세 분석과 개선안

### 1. 일반 대화까지 Worker 작업으로 분류됨

대표 사례:

- “아아 잘 들려”
- “지금 잘 작동하고 있는 거니?”
- 상태 확인이나 개념 질문

이런 입력에도 `plan → execute` 타임라인과 Worker 대기가 표시됐다. 사용자는 Codex와 대화한다고 생각하지만 시스템은 모든 메시지를 코드 작업 요청으로 취급했다.

개선안:

1. 모든 입력을 먼저 Codex 요청 분류기에 전달한다.
2. 결과를 `chat`, `status_query`, `work_request`, `approval`, `retry`, `cancel`로 구조화한다.
3. `chat`과 `status_query`는 Worker를 생성하지 않는다.
4. `work_request`만 실행 계획 미리보기와 승인 단계로 이동한다.
5. 분류 신뢰도가 낮거나 파괴적 작업이면 실행하지 않고 사용자에게 확인한다.

```json
{
  "intent": "work_request",
  "confidence": 0.97,
  "requiresApproval": true,
  "summary": "사용량 표시 UI 구현",
  "risk": "medium"
}
```

완료 기준:

- 인사, 질문, 상태 문의 30개가 Worker를 생성하지 않는다.
- 구현 요청 30개는 실행 전 계획 미리보기를 생성한다.
- 분류 결과와 실제 라우팅 경로가 감사 로그에 남는다.

### 2. Dashboard Run과 실제 Router Run이 분리됨

웹에는 Run ID와 `running` 상태가 있지만 실제 `.agent/runs/<run-id>`가 생성되지 않거나 Gemini Worker가 시작되지 않는 사례가 있었다. Dashboard가 접수용 ID를 만들고, 별도 프로세스가 실제 Run을 만들면서 두 ID의 연결이 끊긴 것이 핵심 문제다.

개선안:

- `requestId`, `dashboardRunId`, `routerRunId`, `processId`를 명시적으로 저장한다.
- Router가 `RUN_CREATED` 이벤트를 기록하기 전까지 상태를 `starting`으로 유지한다.
- 제한 시간 안에 실제 Run이 만들어지지 않으면 `launcher_failed`로 종료한다.
- 화면의 Run 상세에서 모든 연결 ID와 실제 로그 위치를 확인할 수 있게 한다.
- API가 실행 상태를 추측하지 않고 이벤트 저장소를 단일 진실 공급원으로 사용한다.

### 3. 실제 증거가 없는 허위 타임라인

프로세스가 시작 직후 종료됐는데도 화면에는 “계획 수립 완료”, “도구 및 코드 수정 실행”이 표시됐다. 단계가 실제 이벤트가 아니라 예상 시나리오나 경과 시간으로 생성됐기 때문이다.

개선안:

- 단계는 오직 증거 이벤트가 있을 때만 생성한다.
- `PLAN_STARTED`, `PLAN_COMPLETED`, `TOOL_STARTED`, `TOOL_COMPLETED`처럼 시작과 종료를 분리한다.
- 각 이벤트에 `source`, `timestamp`, `attempt`, `evidencePath`를 포함한다.
- 프로세스 시작만 확인된 상태에서는 “실행기 시작 중” 하나만 표시한다.
- 누락된 이벤트를 UI가 임의로 보충하지 않는다.

### 4. 원래 오류가 보존되지 않음

사용자는 “프로세스 종료/상태 기록 불일치”라는 일반 문구만 보고 무엇을 고쳐야 하는지 알 수 없었다. CLI 미설치, 잘못된 경로, PowerShell 버전, 권한, 한글 인코딩 등 서로 다른 원인이 같은 오류로 축약됐다.

개선안:

- Run별 `stdout.log`, `stderr.log`, `process-result.json`을 저장한다.
- `process-result.json`에는 실행 파일, 정제된 인자, 시작·종료 시각, exit code, timeout 여부, 종료 신호를 기록한다.
- 비밀 값과 사용자 홈 경로는 화면 노출 전에 정제한다.
- 사용자 화면에는 짧은 원인, 재시도 가능 여부, 로그 보기 버튼을 제공한다.
- 개발자 상세 화면에서 정제된 원본 stderr를 확인할 수 있게 한다.

### 5. 응답과 이벤트가 스트리밍되지 않음

현재 체감은 CLI 답변이 모두 끝난 후 웹에 한꺼번에 복사되는 방식에 가깝다. 긴 답변에서는 앱이 멈췄는지 추론 중인지 구별할 수 없다.

개선안:

- 대화 응답은 SSE 또는 WebSocket으로 토큰 단위 스트리밍한다.
- Worker의 원시 터미널 출력과 구조화 이벤트 채널을 분리한다.
- 연결이 끊기면 마지막 event sequence 이후부터 재연결한다.
- 2~3초 이상 새 토큰이 없어도 `thinking`, `tool_running`, `waiting_process` 상태를 갱신한다.
- 스트리밍 실패 시 최종 결과 조회로 자동 폴백한다.

### 6. 완료 여부와 현재 책임 주체를 알 수 없음

사용자가 여러 번 “지금 작업 중이냐?”, “끝났냐?”, “어느 정도 됐냐?”고 물어야 했다. 화면이 `running`만 보여주고 현재 Codex, Gemini, 검증기 중 누가 작업 중인지 설명하지 못했다.

개선안:

- 모든 Run에 `currentOwner`, `currentStage`, `lastActivityAt`, `nextExpectedEvent`를 둔다.
- 상단에 `Codex 계획 중`, `Gemini 구현 중`, `테스트 검증 중`, `사용자 승인 대기`를 표시한다.
- 완료·실패·승인 필요 시 브라우저 알림과 앱 내 알림을 한 번만 보낸다.
- 백그라운드 작업이 없으면 명확히 “실행 중인 Worker 없음”으로 표시한다.

### 7. 종료 Worker와 오래된 상태가 남음

작업이 끝났거나 실패했는데도 프로젝트 관제실의 활성 Worker 수가 줄지 않았다. 새로고침해도 같은 상태가 유지돼 실제 프로세스가 살아 있는 것처럼 보였다.

개선안:

- 활성 상태를 `planning`, `running`, `retrying`, `verifying`으로 제한한다.
- 프로세스 종료 이벤트 수신 즉시 활성 목록에서 제거하고 작업 기록으로 이동한다.
- heartbeat가 일정 시간 없으면 `stale`로 전환한 뒤 OS 프로세스와 대조한다.
- 서버 시작 시 디스크 이벤트, compact 상태, 실제 PID를 재조정한다.
- UI의 새로고침은 단순 React 재렌더가 아니라 서버 reconciliation을 요청한다.

### 8. Codex–Gemini 협업 과정이 보이지 않음

사용자는 내부 CLI 전체 대화를 보고 싶은 것이 아니라, 누가 무엇을 맡았고 왜 재시도됐으며 어디서 막혔는지를 알고 싶어 했다.

개선안:

- Git graph처럼 아래에서 위로 진행되는 작업 트리를 제공한다.
- 노드에는 담당자, 시작·종료 시각, 상태, attempt, 변경 파일 수, 검증 결과를 표시한다.
- 노드를 누르면 `agent_response`, `tool ACTIVE/DONE`, `LOAD`, `SAVE`, 테스트 실행 등 상세 이벤트를 펼친다.
- 원시 사고 과정은 노출하지 않고 작업 지시, 도구 호출, 파일 변경, 결과 요약만 보여준다.
- 병렬 Worker는 갈라진 가지로, 통합 검토는 합쳐지는 노드로 표현한다.

### 9. 실패 노드 재시도가 대화에 의존함

단일 Worker나 테스트가 실패해도 사용자가 다시 채팅으로 전체 상황을 설명해야 했다. 이는 컨텍스트를 낭비하고 잘못된 전체 재실행을 유발한다.

개선안:

- 실패 노드에 `재시도`, `수정 지시 후 재시도`, `Codex 진단 요청` 버튼을 제공한다.
- 재시도는 기존 Run과 task ID를 유지하고 attempt만 증가시킨다.
- 성공한 독립 노드는 다시 실행하지 않는다.
- 환경 오류는 결정적 복구 후 자동 재시도하고, 코드 오류만 모델에 전달한다.
- 재시도 한도 초과 또는 정책 위반만 사용자/Codex 검토로 올린다.

### 10. 승인 버튼의 의미가 불명확함

승인이 “대화를 계속한다”는 의미인지, 실제 CLI 실행·파일 수정·병합을 허용하는 것인지 명확하지 않았다.

개선안:

- 버튼 이름을 행위에 맞게 `계획 승인 및 Worker 실행`, `통합 승인`, `main 반영 승인`으로 구분한다.
- 승인 전에 예상 작업, 저장소, 수정 범위, 명령, Worker 수, 위험 수준을 보여준다.
- 승인은 특정 plan hash에 결합하며 계획이 바뀌면 다시 승인받는다.
- 단순 채팅과 상태 조회에는 승인 버튼을 표시하지 않는다.

### 11. 사용량 정보가 일관되지 않음

Codex와 Gemini의 사용량이 같은 한도인지, 남은 비율인지 사용한 비율인지, 언제 초기화되는지 혼란이 있었다. 조회 불가 상태도 영구 오류처럼 보였다.

개선안:

- 공급자별로 `usedPercent`, `remainingPercent`, `resetsAt`, `updatedAt`, `source`를 구분한다.
- 기본 상태는 작은 `조회하기` 버튼으로 표시한다.
- 조회 후에는 `Codex 59% 남음`처럼 방향을 명시한다.
- 마우스를 올리면 한도 종류, 초기화 시각, 마지막 갱신 시각을 표시한다.
- 조회 실패는 `다시 조회`로 표시하며 추정값을 실제 값처럼 보여주지 않는다.

### 12. Windows CLI 실행 환경이 불안정함

대표적으로 다음 문제가 있었다.

- `codex-route` 또는 `agy.exe` 경로를 찾지 못함
- Windows PowerShell에서 `pwsh.exe`를 찾지 못함
- 한글 사용자명과 공백이 포함된 저장소 경로가 깨짐
- 와일드카드와 `Get-Content -Wait` 조합 차이
- Wrapper가 존재하지 않는 고정 경로를 참조함

개선안:

- PowerShell 7, Codex CLI, Gemini CLI, Router 경로를 시작 시 탐색하고 readiness 결과를 표시한다.
- 셸 문자열 연결 대신 실행 파일과 인자 배열을 사용한다.
- 모든 입출력을 UTF-8로 고정하고 한글·공백 경로 통합 테스트를 유지한다.
- 웹에서 실행 전에 진단 화면을 제공하고 실패한 항목별 복구 명령을 보여준다.
- 설치 경로를 코드에 고정하지 않고 설정과 탐색 결과로 관리한다.

## 권장 화면 구조

```text
┌────────────────────────────────────────────────────────────┐
│ Codex × Gemini          Codex 조회 | Gemini 조회 | 연결 정상 │
├────────────────────────────────┬───────────────────────────┤
│ 사용자 ↔ Codex 대화             │ 작업 그래프                │
│                                │                           │
│ 질문은 여기서 즉시 답변          │ Plan ─ Worker A ─ Verify  │
│ 작업은 계획 미리보기 후 승인      │    └ Worker B ↻           │
│ 스트리밍 응답                    │          └ Review ○       │
│                                │                           │
│ [계획 승인 및 Worker 실행]        │ [노드 상세] [재시도]       │
├────────────────────────────────┴───────────────────────────┤
│ 현재: 2 workers · 1 retry · Gemini 구현 중 · 마지막 활동 3초 전 │
└────────────────────────────────────────────────────────────┘
```

모바일이나 좁은 화면에서는 대화와 작업 그래프를 탭으로 분리하되 동일한 Run 선택 상태를 유지한다.

## 권장 이벤트 구조

```json
{
  "eventId": "evt_000123",
  "sequence": 123,
  "requestId": "req_...",
  "dashboardRunId": "run_...",
  "routerRunId": "20260910-...",
  "taskId": "TASK-001",
  "attempt": 2,
  "source": "gemini-worker",
  "type": "TOOL_COMPLETED",
  "status": "completed",
  "occurredAt": "2026-09-11T00:00:00+09:00",
  "summary": "테스트 실행 완료",
  "evidencePath": ".agent/runs/.../test-summary.json"
}
```

필수 원칙:

- 이벤트는 append-only로 저장한다.
- UI는 sequence 순서로 중복 없이 적용한다.
- compact state는 이벤트에서 재생성 가능해야 한다.
- 재연결 시 마지막 sequence 이후 이벤트만 전송한다.
- 상태 변경에는 항상 근거 이벤트가 있어야 한다.

## 구현 우선순위

### 1단계: 신뢰 회복

1. 요청 분류로 일반 대화와 작업 실행을 분리한다.
2. Dashboard Run과 Router Run을 연결한다.
3. stdout, stderr, exit code와 원래 오류를 보존한다.
4. 실제 이벤트가 없는 허위 타임라인을 제거한다.
5. 종료 Worker 정리와 서버 재시작 reconciliation을 구현한다.

### 2단계: 소통 개선

1. Codex 응답 스트리밍을 구현한다.
2. 현재 담당자와 마지막 활동 시각을 표시한다.
3. 완료·실패·승인 필요 알림을 추가한다.
4. 작업 그래프와 노드 상세 이벤트를 구현한다.
5. 실패 노드 단위 재시도를 구현한다.

### 3단계: 운영 편의

1. 승인 단계를 목적별로 구분한다.
2. 사용량 수동 조회와 초기화 시각 표시를 추가한다.
3. 실행 환경 readiness와 복구 안내를 제공한다.
4. 이벤트 검색·필터·내보내기를 제공한다.

## 통합 완료 기준

다음 시나리오가 실제 localhost 환경에서 모두 통과해야 한다.

- “잘 들려?” 입력은 Worker 없이 스트리밍 답변으로 끝난다.
- “버튼 색상을 수정해줘” 입력은 계획 미리보기까지만 진행하고 승인 전에는 파일을 수정하지 않는다.
- 승인 후 실제 Router Run과 Worker가 생성되고 화면 ID로 추적된다.
- Worker의 도구·파일·테스트 이벤트가 작업 그래프에 순서대로 표시된다.
- 브라우저를 새로고침해도 같은 Run의 정확한 상태로 복구된다.
- 서버를 재시작해도 실행 중·완료·실패 상태가 실제 PID 및 디스크 기록과 일치한다.
- 강제 종료 시 exit code와 정제된 stderr가 화면에 표시된다.
- 실제 이벤트가 없는 계획·도구 단계는 표시되지 않는다.
- Worker 완료 즉시 활성 목록에서 사라지고 기록으로 이동한다.
- 실패한 단일 노드만 재시도할 수 있으며 성공한 노드는 다시 실행되지 않는다.
- 완료 후 사용자에게 한 번만 알림이 전달된다.
- 한글 사용자명과 공백이 포함된 Windows 경로에서도 동일하게 동작한다.

## 최종 원칙

이 웹이 해결해야 하는 것은 “로그를 더 많이 보여주는 것”이 아니다. 사용자가 다음 네 가지를 묻지 않아도 알 수 있게 만드는 것이 목표다.

1. 지금 실제로 작업 중인가?
2. 누가 무엇을 하고 있는가?
3. 멈췄다면 어디서 왜 멈췄는가?
4. 내가 지금 해야 할 행동은 무엇인가?

화면의 모든 상태는 실제 프로세스와 이벤트 증거에 연결되어야 한다. 대화는 대화답게 즉시 응답하고, 작업은 작업답게 승인·실행·검증·완료의 경계를 명확하게 보여줘야 한다.
