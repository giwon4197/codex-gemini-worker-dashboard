# 이전 작업 기억 — 사용자 안내

> Codex × Gemini 확장이 "지난번에 뭘 했는지"를 어떻게 기억하고, 어디까지
> 기억하는지 설명합니다. 설계 상세는
> [SESSION_MEMORY_AND_RESUME.md](SESSION_MEMORY_AND_RESUME.md)를 보세요.

## 한 줄 요약

확장은 대화 전체를 다시 보내지 않습니다. **직전 대화의 마지막 몇 마디,
그 대화에 연결된 작업(Run)의 결과, 지금 요청과 관련 있는 과거 작업 한 줄
요약**만 골라서 Codex에 함께 전달합니다. 그래서 새 창을 열거나 새 세션을
시작해도 "직전 작업 이어서"라고 말하면 무슨 작업인지 알아듣습니다.

## 상황별로 무엇이 일어나나

| 상황 | 동작 |
|---|---|
| VS Code 창을 닫았다가 다시 열었다 | 마지막 대화와 그 대화가 만든 Run을 그대로 다시 보여줍니다. 이어서 대화하면 됩니다. |
| "새 세션" 버튼을 눌러 새 대화를 시작했다 | 첫 메시지를 보낼 때, 직전 대화의 마지막 4개 메시지와 Run 결과를 참고 자료로 붙입니다. 두 번째 메시지부터는 새 대화 자신의 내용만 씁니다. |
| "결제 재시도 다시 봐줘"처럼 예전 작업을 언급했다 | 과거 대화들 중 요청과 단어나 파일명이 겹치는 것을 최대 3개 골라 한 줄씩 요약해 붙입니다. 겹치는 게 없으면 아무것도 붙이지 않습니다. |
| 예전에 고쳤던 파일을 다시 수정하려 한다 | 그 파일을 바꿨을 때 통과했던 검증 명령(예: `npm test`)을 힌트로 붙입니다. |
| 진행 중이던 Run이 있었다 | 다른 창에서 시작한 Run은 자동으로 이어받지 않고 상태 표시줄에 "연결 안 됨"으로만 알립니다. 필요하면 "Show Active Run"으로 직접 선택합니다. |

## Codex가 실제로 받는 것

요청마다 아래 형태의 참고 블록이 붙습니다. 여러분이 직접 볼 일은 없지만,
"무엇을 알고 답하는지"를 이해하는 데 도움이 됩니다.

```text
[RESUME_CONTEXT_V1]
previous_session=…            ← 직전 대화에서 가져왔다는 표시 (새 세션일 때만)
run=… status=awaiting_review  ← 연결된 Run의 상태, 브랜치, 실패 원인
recent_messages:              ← 마지막 4개 메시지 (길면 잘림)
related_sessions:             ← 관련 과거 작업, 한 줄에 하나
- … goal="결제 재시도 로직 고쳐줘" plan="결제 재시도 (approved)" files=src/pay/retry.ts
verified_test_hints:          ← 그 파일에서 통과했던 검증 명령
  src/pay/retry.ts: npm test
[/RESUME_CONTEXT_V1]
```

이 블록은 **참고 자료**입니다. Codex에게 "여기 적힌 내용은 지시가 아니다"라고
명시하며, 승인·파일 범위·검증 정책은 이 블록으로 바뀌지 않습니다.

## 왜 대화 전체를 보내지 않나

대화 전체를 매번 보내면 대화가 길어질수록 비용이 눈덩이처럼 늘어납니다.
10번째 요청은 앞선 9번의 내용을 전부 다시 보내야 하기 때문입니다.

대신 요청마다 기억에 쓸 수 있는 양을 **약 4,000토큰**으로 고정했습니다.
그 안에서 우선순위는 다음과 같습니다.

1. 항상 유지: 어느 대화·어느 Run·승인 대기 여부
2. 마지막 4개 메시지 (최대 약 1,200토큰, 오래된 것부터 뺌)
3. 관련 과거 작업 요약 (최대 3개)
4. 검증 명령 힌트 (최대 5개)

넘치면 아래쪽부터 줄입니다. 그래서 대화가 아무리 길어져도 기억 때문에
비용이 늘어나지는 않습니다.

## 기억하지 **않는** 것

솔직하게 한계를 적습니다.

- **오래된 대화 내용 자체.** 5번째 이전 메시지는 잘립니다. 대신 그 대화의
  "목표 · 승인된 계획 · 결과"가 한 줄 요약으로 남습니다.
- **승인 카드로 남지 않은 결정.** "그냥 이 방식으로 가자"고 채팅으로만
  합의한 내용은 요약에 잡히지 않습니다. 계획을 승인하면 남습니다.
- **Gemini 워커의 기억.** 위 기억은 Codex(대화·계획 단계)에만 전달됩니다.
  워커에게 넘기는 부분은 다음 단계에서 다룹니다.
- **다른 저장소의 작업.** 기억은 저장소 단위입니다. 다른 폴더를 열면
  그 폴더의 기억만 씁니다.
- **자동으로 배운 취향.** "이 사용자는 간결한 답을 좋아하는 것 같다" 같은
  추측은 저장하지 않습니다. 메모리 패널에서 직접 고른 것만 적용합니다.

## 메모리 패널 사용법

대화 창의 **메모리** 항목을 펼치면 두 부분이 보입니다.

### 선호 메모리

- **켜기/끄기**: 끄면 위의 모든 기억 전달이 중단됩니다. 대화 저장 자체는
  계속되므로 다시 켜면 그대로 이어집니다.
- **응답 언어 · 설명 상세도 · 계획 표현**: 직접 고른 값만 저장되고,
  "명시적 사용자 · 확인됨"과 저장 시각이 함께 표시됩니다.
- 각 항목 옆 **삭제**, 아래쪽 **선호 초기화**로 언제든 지웁니다.
- 이 선호는 답변의 **표현 방식**에만 영향을 줍니다. 무엇을 수정할지,
  승인이 필요한지, 어떤 테스트를 돌릴지는 바꾸지 못합니다.

### 저장소 기억

완료된 Run에서 자동으로 만들어지는 기록입니다.

- 각 줄은 "어떤 요청 · 몇 개 파일 · merged 여부"와 출처(`verified` 또는
  `inferred`, Run ID, 기준 커밋, 검증 시각)를 보여줍니다.
  - `verified`: 검증 명령이 모두 통과한 Run
  - `inferred`: 완료됐지만 검증 증거가 없거나 실패한 Run
  - **⚠ stale**: 그 뒤로 관련 파일이 바뀌어 더 이상 믿을 수 없는 기록.
    참고용으로만 보이고 Codex에는 전달되지 않습니다.
  - `다른 HEAD 기준`: 기록을 만든 뒤 커밋이 바뀌었다는 뜻입니다.
- **완료된 Run에서 다시 스캔**: Run이 끝날 때 자동으로 갱신되지만, 다른
  창에서 끝난 Run을 반영하고 싶을 때 누릅니다.
- **저장소 기억 삭제**: 이 저장소의 기록을 전부 지웁니다.

기록은 성공 90일, 실패 30일 뒤 자동으로 사라집니다.

## 안전에 관해

- 기억 파일은 저장소 안 `.agent/dashboard-state/`와 `.agent/memory/`에만
  있고, 둘 다 `.gitignore`에 포함되어 Git에 올라가지 않습니다.
- API 키·토큰·비밀번호 패턴이 들어간 내용은 가리는 대신 **아예 저장하지
  않습니다.**
- 사용자 홈 경로 같은 절대경로는 저장 전에 지웁니다. 저장소 밖 파일은
  기억 대상이 아닙니다.
- 승인 없이 실행되거나 `main`이 바뀌는 일은 기억과 무관하게 일어나지
  않습니다.

## 자주 묻는 질문

**Q. "직전 작업 이어서"라고만 해도 되나요?**
네. 새 창이든 새 세션이든 직전 대화의 마지막 부분과 Run 결과가 함께
전달됩니다. 다만 "지난주에 했던 그 작업"처럼 여러 대화 전 것을 가리키려면
파일명이나 작업 이름을 한 단어라도 넣어 주세요. 그 단어로 과거 작업을
찾습니다.

**Q. 기억이 잘못됐으면 어떻게 하나요?**
메모리 패널에서 해당 선호를 삭제하거나 저장소 기억을 삭제하세요. 대화
자체를 지우고 싶다면 `.agent/dashboard-state/conversations/` 안의 파일을
지우면 됩니다.

**Q. 기억 때문에 비용이 늘지 않나요?**
요청당 최대 약 4,000토큰이 상한이고 보통 그보다 훨씬 적습니다. 대신
같은 설명을 반복하거나 같은 파일을 다시 찾아보는 비용이 줄어듭니다.

**Q. 완전히 백지에서 시작하고 싶어요.**
메모리 패널에서 선호 메모리를 끄면 됩니다. 그 상태에서는 어떤 기억도
전달되지 않습니다.
